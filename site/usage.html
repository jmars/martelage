Verify: the common case

You have a package directory. You run the reference validator against it. That is the whole procedure — there is nothing to install, no account, no key, no network:

sh validator/martelage-verify vectors/01-minimal-conformant/pkg

The anchor block says, in words, that no one but the producer holds this digest. The residual block is the §3.3 sentence, printed on every run that names a package. Exit codes

The exit code is the verdict; the tail of the output is not. The four codes are the standard's (§10.3 MA-70, and README.md):

The exit codes (§10.3)
code meaning
0 CONFORMANT — every check the run could perform passed. An unanchored package exits 0; the NOT-ANCHORED line has been printed.
1 NON-CONFORMANT — a check failed: a digest, a length, a gap, a broken predecessor link, a torn line, a manifest count, an unknown scope word, an unsupported version, a chain break against --prev-package, a claimed anchor that is malformed or that the evidence contradicts.
2 USAGE OR UNREADABLE — the invocation is wrong, or an input could not be read (an unreadable file is not an absence).
3 CANNOT DECIDE — an input the validator needs to decide is absent: anchor evidence for a claimed anchor, trust anchors for P3, or a profile-specific verifier this validator is not. The validator MUST name the missing input.

Why code 3 exists. An instrument that cannot return "undecided" returns something else instead. A claimed anchor that cannot be checked is neither conformant nor refuted, and reporting it as either would be a false statement; it is not conformant enough to pass, so 3 is non-zero (§10.3). This is not a nicety — it is the same discipline as the residual: the format says what it could not establish.

Verify without any tooling

The manifest is canonical and lists every file with its digest, so a verifier with nothing but a POSIX shell can check the file set without any validator. This one-liner is a normative property of the format: a manifest whose canonical form does not admit it is non-conformant (§4.6 MA-21).

grep -o '{"path":"[^"]*","sha256":"[0-9a-f]*"' package.json |
  sed 's/{"path":"\([^"]*\)","sha256":"\([0-9a-f]*\)"/\2  \1/' > SHA256SUMS
sha256sum -c SHA256SUMS

MEASURED, run from inside a copy of vectors/01-minimal-conformant/pkg made in a temporary directory — the one-liner writes SHA256SUMS into the current directory, so do not run it inside the repository unless you mean to add that file. The three lines below are the written SHA256SUMS followed by sha256sum -c, exit code 0:

abf920fbb49003e1b06badc085e74f8396713bca64d2f123eccdb256e6a36bad  records.jsonl
798dab2402394de24954a4e5d0b8c806d8185ac2e54a95ec3ef22e1aeeba807f  notes.md
records.jsonl: OK
notes.md: OK

What that check covers is the file set: every listed file present, and each file's bytes equal to the digest the manifest states. What it does not cover is everything above the file list — the record envelopes, the per-stream sequence and predecessor chain, the manifest counts, the scope vocabulary and the anchor claim (INTERPRETATION, from §4.4 and §7). For those you need the validator.

Produce: what a second project must build

There is no library and no service. Production is decentralised and cheap; checking is centralised and shared — an adopter does not reimplement the validator, it runs the published one, or reads it and writes its own against the specification (Annex F). A project that already writes dated records to durable files needs exactly two things:

  1. An emitter that puts its records into the envelope of §6.2: canonicalise each body, compute body_sha, assign stream and seq, wire prev, print the stream manifest first. For a project whose records are already one JSON object per line, Annex F prices this at roughly 80–120 lines in any language.
  2. A packager that lists its files with digests, writes a canonical manifest with an honest scope, a prev from a one-line state file, and anchored:false — Annex F prices it at roughly 60–100 lines.

Those two line counts are the standard's own estimate (Annex F), not a measurement of any particular project; treat them as a PROJECTION in the §0.4 sense.

Annex E is a worked package written out by hand with printf and sha256sum: two files, one shell, no network, no keys, no service. It is the whole of what a second project must produce to start, and a stranger can copy it. README.md records that executing that example verbatim, in an empty directory, with nothing from the repository on the path except the validator, produces a package the validator reports CONFORMANT (exit 0) — that is the README's measurement; this page did not re-run it.

Do not expect a validator to live inside a package. A package is not required to carry one, and a validator found inside a package proves nothing about that package, because it sits inside the directory the operator can rewrite; checkability comes from the published validator or from the verifier's own implementation, obtained through a channel the operator does not control (§4.5 MA-20).

Chain and anchor: the two layers that look outside the package

Two verifier inputs arm the two layers that reach beyond the package directory (§10.2 MA-69). Neither is required for the base tier — and an unarmed layer must never read as a pass (§7, §10.4 item 6).

--prev-package DIR — arms layer 3

Without it, a record dropped between two packages is invisible: the omission happened outside the package you hold, and nothing inside this package records that it ever existed. That is the whole power of the layer, and it is bounded exactly as §7.4.3 says: it converts a silent omission into a break visible one package later — if someone kept the earlier package — and it does not stop an operator who starts a fresh chain and is watched by nobody (§7.4.3 MA-51).

"Anchored" is a property of (package, verifier's evidence), not of the package alone: the same package is verified-anchored for a verifier who brought the holder's digest, and cannot be decided for one who did not (§9.5 MA-66). Which profile a package names decides what a verifier can do with its anchor, and one of the three is an EU qualified seal. The profiles have their own section.

The anchor slot: three named profiles

The anchor is a slot with named profiles, not one vendor: §9.3 names three at this version and leaves the slot open to others (§9.1(c) MA-61). It gets a section of its own because layer 4 is the only layer whose witness the operator cannot recompute (§7.5 MA-52) — and because the profile a package names is the thing that decides what a verifier can actually check. What no profile changes is the claim's force: an anchor never says the record is true or complete, only that a digest existed, at a time, by someone else (§3.7 MA-15, §7.5 MA-52).

The three anchor profiles at this version (§9.3)
profile wire string — the value of anchor.profile what the base validator does with it
P1 p1-second-party-digest Verifies it fully: the holder's digest must equal the package digest (§9.3 MA-64).
P2 p2-append-only-log Compares a digest the log states to the package digest. A digest that contradicts the package is a refusal (exit 1); a digest that matches still leaves inclusion undecided, so it reports exit 3 and names what it could and could not check (§9.3, §10.3 MA-70).
P3 p3-eidas-qualified-seal-asic-e Cannot verify a signature, so it reports exit 3 and names the profile-specific verifier it is not (§9.3, §10.3 MA-70).

P1, P2 and P3 are labels for those strings, never values: a manifest writing P3, or the profile's name in any other spelling, is refused as an unknown profile (§9.2 MA-63, §9.4 MA-65). The wire string is what a validator matches.

p3-eidas-qualified-seal-asic-e — the EU qualified seal

P3 is the profile for a deployment that already has to answer to EU law. In the standard's own terms it is an ETSI EN 319 162-1 ASiC-E container holding the package files with a CAdES or XAdES signature over their digests, created by a legal person other than the operator, with a qualified electronic time stamp and optional long-term validation (§9.3 MA-64). The party who seals is the point: a seal is only an anchor because someone the operator is not made it.

The claim is a reference, not the seal. A manifest cannot carry a value derived from its own digest (§9.1a MA-62), so the container and the trust anchors stay on the verifier's side and the claim only says where to get them. This is the claim shape, verbatim from §9.3:

{"container":…,"sealer":…,"seal":"qualified-electronic-seal",
 "timestamp":"qualified"|"none","ltv":<bool>}

What the reference validator does with that claim is nothing, and it says so. It cannot verify a signature — that needs a signature verifier and trust anchors — so it reports exit code 3 CANNOT DECIDE and names the profile-specific verifier requirement (§9.3, §10.3 MA-70). That is the standard's own rule applied rather than an omission: a claimed anchor the verifier cannot verify MUST NOT pass (§9.1(e) MA-61). Nor does a specialised verifier get a lighter contract for being specialised — a profile-specific verifier MUST report under §10, the same exit codes and the same report items (§9.3, §10.4 MA-71) — so "we sealed it" is not a way to skip the report.

Status: built, by a second implementation. The base validator still stops at exit code 3 and still names the profile-specific verifier it is not — that has not changed and is not going to, because §9.1(b) keeps keys and trust anchors out of the base tier. The verifier it names is validator/p3-verify: a second implementation that shares no code with martelage-verify, runs under python3 and calls the openssl binary for every cryptographic operation. It has no network path at all: it never downloads anything, never opens a URL, never writes an OCSP request and never contacts an OCSP responder. Revocation is checked only against the material the person running it hands it — --revocation FILE for a CRL, --ocsp-response FILE for an OCSP response, --revocation-dir DIR for a directory of both — and without any of them revocation is not checked and the report says so.

validator/p3-verify \
  --container vectors/34-seal-verified/seal.asice \
  --trust-anchors vectors/pki/anchors \
  --operator-cert vectors/pki/operator.crt.pem \
  vectors/34-seal-verified/pkg                      # exit 0

It takes the container and the anchors on the verifier's side, as §10.2 (MA-69) says a P3 input must be, plus inputs of its own: --operator-cert, the operator's certificate, and optionally revocation material — --revocation, --ocsp-response or --revocation-dir. Without the operator certificate the "legal person other than the operator" clause cannot be checked, so the run reports 3 for that clause and says the input is missing. It never assumes the signer is someone else — which is why no P3 run reaches exit 0 without it.

What --revocation takes, and what it establishes. A CRL, PEM or DER, read from a file the verifier was given; repeat it once per CA in the chain, because a CRL speaks only for the certificates its own issuer signed. With it the verifier checks its own signature against a certificate the run holds, checks that its window (thisUpdate … nextUpdate) contains now, and checks every certificate in the established chain that the CRL speaks for: a listed certificate refuses the container and the report names the certificate, the CRL, the revocation date and the reason. A certificate no supplied CRL speaks for is reported as not checked and makes the run 3 — never "not revoked". A CRL that has expired, is not yet valid, or whose signature does not verify is reported unusable and the run does not claim revocation was checked.

What --ocsp-response takes, and what it establishes. An OCSP response — DER, or PEM with the standard header — read from a file the verifier was given and read with openssl ocsp -respin. No request is written, no responder is contacted: the response is material you were handed, and this tool has no network path at all. It checks the response's own signature against a signer the certificate's issuer authorised — the issuer itself, or a responder the issuer issued — and requires that signer's chain to reach a supplied anchor; and it requires the response's CertID to name the certificate being checked, because an OCSP answer is about one certificate and never about a set. A revoked status refuses the container (1), naming the certificate, the responder, thisUpdate, nextUpdate, the revocation time and the reason. A good status is checked and clean for the certificate the response names, and is never carried across to another one. unknown, an expired or not-yet-valid window, an unverifiable signer, an unsuccessful response status, or a response that names no certificate of this chain is its own stated outcome and makes the run 3 — none of them reads as a pass.

What --revocation-dir takes. A directory of revocation material, so a chain does not need one flag per file. Every regular file in it that parses as a CRL or as an OCSP response is applied by the rules above, and the report names, per certificate, which supplied file covered it. A file that parses as neither is reported and makes the run 3: a verifier that silently skips material it was handed is claiming more than it checked. It is a separate flag from --revocation because that flag's published contract is a single file — a path that turns out to be a directory should be an error, not a different check. The three flags combine, and the coverage rule does not soften: every certificate in the chain must be spoken for by something, or the run is 3 naming what is uncovered. What remains uncheckable is said in the same breath: no OCSP response is ever requested, no CRL is ever downloaded, a revocation published after a CRL's or a response's nextUpdate is invisible, a supplied status is the status now and not at the claimed time, and long-term validation is still never validated.

The clause is checked over the whole signer set. A signature entry may carry more than one signer, and the operator only has to be one of them. The verifier enumerates every signer of every entry from openssl's -signer output, holds that count against the signerInfos the entry itself states, refuses the container if the two disagree, and compares every one of them with --operator-cert: if any signer is the operator, the run refuses and names it. The report prints the signer count and every signer's subject, window and public-key digest — never a single subject standing in for "the signer". The same set is what the certificate-date check runs over: every signer, every certificate in the chain each signer reaches, and the timestamping authority's own chain, all held to the time the verified token establishes and never to this host's clock.

What p3-verify checks, and the four exit codes (§10.3 MA-70)
code meaning for P3
0 CONFORMANT — the signature entry is the construction this verifier implements (a detached CAdES over the manifest), the container is well-formed (no duplicate entry name, every covered path inside the package), the CAdES signature verifies over the ASiC manifest, every signer of every signature entry chains to a supplied anchor and none of them is a CA, every sealed digest is the package's, the RFC 3161 token verified, every certificate the run established — every signer, the whole chain, the TSA's own chain — was valid at the claimed time, no signer's key is the operator's, and — only if --revocation was given — every certificate a supplied CRL speaks for is absent from it. Revocation unarmed is not part of this verdict and is reported as unarmed.
1 NON-CONFORMANT — a signature entry whose content is embedded rather than detached over the manifest: a shape this verifier does not implement, refused by name before anything else is accused, together with the EN 319 162-1 concatenated-digest form and XAdES; a malformed container (a wrong mimetype, a duplicate ZIP entry name, a covered path that leaves the package, an entry the manifest lists and the ZIP does not hold, a sealed digest that no longer matches the file on disk), a signature that does not verify, a signer certificate that is a CA, any signer or chain certificate that was not valid at the claimed time, a token from a timestamping authority that was not, a seal made with the operator's own key or co-signed with it, a certificate a supplied CRL lists — or a supplied OCSP response reports — as revoked, or --require-timestamp given with no token.

A signature that verifies but reaches no supplied anchor is this code, not a refusal: the verifier was not given the anchor that decides it (§9.5 MA-66). So is a certificate no supplied material speaks for: "nothing said" is not "nothing revoked".

What it still cannot check, on every run. The verifier prints a section headed not checkable by this verifier (every run) before its verdict — and prints it to stderr on an exit-2 run as well, so "on every run" is true of the runs that have no report — and the list below is that section's content, and it is printed in the state the run is actually in: revocation — unarmed, the entry says no CRL and no OCSP response is read and no OCSP responder is contacted, so "valid at the claimed time" means the certificate dates and never revocation status; armed, it says exactly which material was used, with each CRL's issuer, thisUpdate, nextUpdate and entry count and each response's signer, status and window, that a certificate no supplied material speaks for has no revocation status here, that a revocation published after a CRL's or a response's nextUpdate is invisible, and that a supplied status is the status now and not at the claimed time; long-term validation — LTV material is reported present or absent and never validated; the truth and completeness of the records, which is limit (iii) below and is kept distinct from the residual of §3.3; the signer's legal identity beyond the subject its certificate claims; whether the certificate was issued for sealing at all (this standard defines no key-usage profile for a seal, so the chain is verified with -purpose any and that is said rather than assumed — the basicConstraints CA bit is the one key-usage-shaped property that is checked, because a CA is not a sealing party); and a re-forged history, limit (ii). A run that could not check something never reads as having checked it, and when no verified time exists the date question is reported CANNOT DECIDE rather than skipped.

What it is not. Not a qualified trust service, not an eIDAS certification, and not a claim of compliance with ETSI EN 319 162-1. The container shape it verifies is the manifest-signature form — a detached CAdES over META-INF/manifest.xml, carrying the covered files' digests in that manifest — and the tool says so in its own report, because the EN 319 162-1 multi-file concatenated-digest form is not what it parses and it will not report that as verified. A container of another shape is refused rather than absorbed: an embedded-content CMS, the concatenated-digest form and XAdES are all shapes this verifier does not implement, and a run that meets one says which shape it met instead of reporting it as a detached signature it is not. It does not verify XAdES. It is not a revocation service either: --revocation, --ocsp-response and --revocation-dir check the material they are handed and nothing else — no live OCSP, no CRL download, no OCSP request, no long-term validation. It does not make the base validator verify seals, and it does not change the base tier's tool list (§10.1 MA-68).

The fixtures are a throwaway test PKI under vectors/pki/ — two roots, an intermediate, a second intermediate with the same key and subject that expired in 2021, a sealer, a second sealer under the same intermediate, a sealer under the withheld root, an expired sealer, the operator, a timestamping authority and a second TSA certificate with the same key and subject that expired in 2021 — with its private keys committed on purpose, because a vector that cannot be rebuilt from what is in the tree is not reproducible. The dates are fixed with -not_before/-not_after, so the expired-signer, expired-intermediate and expired-TSA vectors are expired on any host at any time; the keys are regenerated on each run, so sh tools/mkpki.sh && sh tools/mkp3.sh rebuilds the PKI and the containers together. The CRLs those vectors hand the verifier are built by tools/mkcrl.sh — one per CA in the chain, plus a revoked entry, a window that ended in 2021 and a CRL from a CA that issued nothing in the chain — and the OCSP responses by tools/mkocsp.sh, which signs them with a responder intermediate A issued and, for the unanchored arm, with one that is self-signed. Those responses are then re-dated and re-signed by the same responder key so their windows are the same fixed dates the CRLs use: openssl ocsp stamps a response with the build second and refuses a non-positive window, so a shipped "expired response" is impossible without that step. So sh tools/mkpki.sh && sh tools/mkcrl.sh && sh tools/mkocsp.sh && sh tools/mkp3.sh rebuilds the PKI, the revocation material and the containers together. All of them run offline, open no port and need only openssl and python3. Twenty-five vectors (34–58) cover this profile, each with an arm that passes and an arm that fails, differing by one thing: a digest that moved, an anchor that is withheld, an operator that sealed, an operator that co-signed, a CA used as the sealing party, an intermediate or a TSA that expired, a ZIP entry name that appears twice, a covered path that leaves the package, a signature whose content is embedded instead of detached, a sealer on a CRL, a CRL that lists nobody, a CRL from another CA, a CRL that has expired, a sealer on an OCSP response, a response that says good, a response whose window ended in 2021, a response signed by a responder that chains to nothing, a directory of both kinds in which one certificate stays uncovered, and a directory holding one file that is not revocation material at all.

§9.3 requires three limits to be stated wherever P3 is offered. They are the profile's terms, not its small print:

  • (i) A seal made with the operator's own key is worthless against the operator, because they hold the key. That is why the verifier compares every signer of every signature entry: a co-signer does not launder a self-seal, and "the first signer was someone else" is not the clause being checked. Only a seal by a different legal person, or a qualified time stamp, is out of their reach — and even then the trust service attests only what it was handed (§9.3).
  • (ii) A single seal does not stop a re-forged history. The operator can doctor a package and have that sealed. What defeats it is custody of prior packages by the other party, so the seal multiplies the chain and does not replace it (§9.3).
  • (iii) The legal presumption that attaches to a qualified seal is a presumption about integrity and origin, not a technical guarantee of truth or completeness, and it must be kept distinct from the residual of §3.3 in any document that cites both (§9.3).

What P3 rests on is in Annex B, and nothing beyond it is claimed here. Item 10 adopts eIDAS (Regulation (EU) No 910/2014) and ETSI EN 319 162-1 as the basis of P3, with the three limits above, and records why the presumption stops where it does: it attaches to the integrity and origin of the sealed data, not to its truth or completeness. Item 11 records eIDAS 2.0 (Regulation (EU) 2024/1183) as introducing the EU Digital Identity Wallet and qualified attestations of attributes about persons — and marks the consequence a PROJECTION in the §0.4 sense (MA-4): no change for a package at this version, because the seal, timestamp and preservation instruments P3 uses are the 910/2014 ones (Annex B items 10–11).

What you should not expect

A validator that did not say what it cannot check would be an advertisement. Every validator must admit the following (§10.7 MA-74):

  • whether the record is true;
  • whether the package is complete — all that ever existed;
  • anything that happened before the first observation or the first anchor (§3.5);
  • the producer's binaries;
  • the honesty of a witness, including a same-host witness (§3.6);
  • where a witness runs, or whether it is outside the audited subject's reach: the package can say so in bound[] or in its scope, and that statement is the producer's claim, not a checked fact;
  • whether a subject.id is a digest rather than a hostname or an account name: a validator refuses the path shapes it can see and cannot distinguish the rest (§5.2.3);
  • who may read the records: a payload's own readability classification is a classification by the publisher, and this standard enforces nothing about it — a validator only echoes it.

The same limits seen from the package's side — what a package is not, and the residual every validator prints — are on the first page. In one line: a package proves what it contains was not altered after it left; it cannot prove it is all there was, and against an operator who rewrote everything before the first anchor it proves nothing.

Where the evidence lives

The repository ships fifty-eight hand-made packages under vectors/, each with an expected.txt recording the run, the expected exit code, the literal lines it must print, and the MA- identifiers the case exercises (MEASURED: 58 directories, 58 expected.txt files). None of them is exported from a producer system; they were constructed for the standard (README.md).

A standard whose only validator has never rejected anything is a description of its author's output. So the claim that the validator can fail is itself measured: take a copy of validator/martelage-verify, delete the one line that compares a record's prev to its predecessor's body_sha (line 828 of the file as shipped), leave everything else alone — sh -n on the mutant is clean — and run the vector built for exactly that check. MEASURED on this tree, both runs trimmed to the refusal block and the verdict:

# as shipped
$ sh validator/martelage-verify vectors/02-broken-predecessor/pkg
refusals
  payload: records.jsonl stream 'note': prev at seq 2 does not name seq 1; 

verdict      NON-CONFORMANT
exit=1

# mutant: line 821 deleted
$ sh /tmp/noprev vectors/02-broken-predecessor/pkg
refusals
  none

verdict      CONFORMANT
exit=0

The mutant still reports 0 on vectors/01-minimal-conformant — the mutation removed that check and nothing else (MEASURED). Vector 02 was built for exactly this: its sequence numbers, counts, head and every digest are consistent, so the prev comparison is the only check that can catch it. README.md lists one such mutant for each check added by review; a check whose removal changes nothing is not load-bearing.
